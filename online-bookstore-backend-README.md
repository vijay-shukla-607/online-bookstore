# Online Bookstore Backend — Local Run & API Testing Guide

This guide is for testing **the backend only** . It covers prerequisites, startup, sample data, authentication, all REST endpoints, Postman request examples, and expected responses.

> **Local setup:** The default profile uses an H2 in-memory database. You do not need to install MySQL, create a database, or edit configuration files to start the backend. The application seeds three sample books and a local administrator on startup when the relevant tables are empty. H2 data is reset when the backend process stops.

## 1. Prerequisites

Install JDK 17 and Maven 3.9 or later. Open a **new** PowerShell window after installing/configuring them.

```powershell
java -version
javac -version
mvn -version
```

Confirm Java reports version 17 and Maven reports a Java 17 runtime. If `mvn` is not recognized, fix Maven's `PATH` before continuing.

## 2. Do I need to change any files?

**No changes are required for a normal local backend test.** The default `application.yml` configures H2 in memory on port 8080. The project has a development-only JWT fallback secret and enables the H2 console for local use. Do not use these development defaults in a deployed/shared environment.

Optional local overrides can be supplied as environment variables, but are not needed for the first test:

- `PORT` — API port (default `8080`)
- `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` — database settings
- `JWT_SECRET` — override the development JWT secret
- `JWT_EXPIRATION_MINUTES` — token lifetime (default `60`)
- `H2_CONSOLE_ENABLED` — H2 console toggle
- `APP_CORS_ORIGINS` — allowed frontend origin (not needed for Postman)

## 3. Build and start the backend

Open PowerShell in the project root, then run:

```powershell
cd backend
mvn clean install
```

Resolve any test failures before continuing. To start the API, run in the same `backend` directory:

```powershell
mvn spring-boot:run
```

Keep this terminal open. The base URL is:

```text
http://localhost:8080
```

To stop the backend, press `Ctrl+C`. To start fresh, restart it; the in-memory database will be recreated and the startup seed will run again.

### Verify it started

Open a second terminal or Postman and call:

```http
GET http://localhost:8080/api/books
```

Expected status: `200 OK` with a JSON array of books.

## 4. Is test data loaded automatically?

**Yes.** On startup, `SeedData` inserts sample books if the books table is empty. A fresh local database should contain these books:

| Title | Author | Price | Stock |
|---|---|---:|---:|
| Clean Code | Robert C. Martin | 42.50 | 25 |
| Effective Java | Joshua Bloch | 48.00 | 20 |
| Designing Data-Intensive Applications | Martin Kleppmann | 55.00 | 12 |

IDs are generated by the database. They may be `1`, `2`, and `3` in a fresh H2 database, but **always use IDs returned by your own API response**.

The local development admin account is seeded by default:

- Email: `admin@bookstore.local`
- Password: `ChangeMe123!`
- Role: `ADMIN`

These credentials are only for local testing. Do not reuse them outside your local environment. Customer accounts are created through the registration API. Cart and order data are created by your test requests; they are not pre-seeded.

## 5. Test with Postman

1. Start the backend and keep it running.
2. In Postman, create a collection called `Online Bookstore - Backend`.
3. Create a collection variable `baseUrl` with value `http://localhost:8080`.
4. For JSON request bodies, select **Body → raw → JSON**.
5. For protected endpoints, select **Authorization → Bearer Token** and paste the token returned by registration/login. You can create collection variables `customerToken` and `adminToken` for convenience.

### Test 1 — List seeded books (public)

```http
GET {{baseUrl}}/api/books
```

Expected: `200 OK`. Note a real `id` from the response for later requests.

Optional search:

```http
GET {{baseUrl}}/api/books?search=Java
```

### Test 2 — Register a customer

```http
POST {{baseUrl}}/api/auth/register
Content-Type: application/json
```

```json
{
  "email": "customer1@example.com",
  "password": "Customer123!"
}
```

Expected: `201 Created`, with a response containing `token`, `tokenType`, `expiresInSeconds`, `email`, and `role`. Save the token as `customerToken`. Use a new email if the address is already registered; duplicate registration should return `409 Conflict`.

### Test 3 — Login as customer

```http
POST {{baseUrl}}/api/auth/login
Content-Type: application/json
```

```json
{
  "email": "customer1@example.com",
  "password": "Customer123!"
}
```

Expected: `200 OK`. Save the returned token as `customerToken`. A wrong password should return `401 Unauthorized`.

### Test 4 — Get one book

Replace `{bookId}` with an ID returned by `GET /api/books`:

```http
GET {{baseUrl}}/api/books/{bookId}
```

Expected: `200 OK`. An unknown ID should return `404 Not Found`.

### Test 5 — View an empty cart

Set Authorization to **Bearer Token** using `{{customerToken}}`.

```http
GET {{baseUrl}}/api/cart
```

Expected for a new customer: `200 OK` with `items: []` and `total: 0`.

### Test 6 — Add a book to the cart

Replace `1` with a real book ID from the list:

```http
POST {{baseUrl}}/api/cart/items
Authorization: Bearer {{customerToken}}
Content-Type: application/json
```

```json
{
  "bookId": 1,
  "quantity": 2
}
```

Expected: `201 Created`. For Clean Code at `42.50`, two copies produce a line total and cart total of `85.00`. The server calculates price from the database; the request does not accept a client-supplied price.

### Test 7 — Update cart quantity

```http
PATCH {{baseUrl}}/api/cart/items/{bookId}
Authorization: Bearer {{customerToken}}
Content-Type: application/json
```

```json
{
  "quantity": 3
}
```

Expected: `200 OK`; the response total reflects three copies at the stored price. Quantity must be between 1 and 1000 and cannot exceed available stock.

### Test 8 — Remove a cart item

```http
DELETE {{baseUrl}}/api/cart/items/{bookId}
Authorization: Bearer {{customerToken}}
```

Expected: `204 No Content` (no response body).

### Test 9 — Add item and checkout

Add an item again using Test 6, then call checkout (no request body is needed):

```http
POST {{baseUrl}}/api/orders/checkout
Authorization: Bearer {{customerToken}}
```

Expected: `201 Created` with an order ID, status, timestamp, total, and order items. For two Clean Code books the total should be `85.00`, assuming the current price remains `42.50` and stock is available. Checkout is not connected to a payment provider.

After checkout, call `GET {{baseUrl}}/api/cart`; expected cart is empty. Calling checkout again with an empty cart should return `400 Bad Request`.

### Test 10 — Order history and details

```http
GET {{baseUrl}}/api/orders
Authorization: Bearer {{customerToken}}
```

Expected: `200 OK` with this customer's orders.

```http
GET {{baseUrl}}/api/orders/{orderId}
Authorization: Bearer {{customerToken}}
```

Expected: `200 OK` for the customer's own order. A customer must not be able to access another customer's order.

### Test 11 — Login as admin

```http

Content-Type: application/json
```

```json

  "email": "admin@bookstore.local",
```

Expected: `200 OK` with `role: ADMIN`. Save the returned token as `adminToken`.

### Test 12 — Create a book (admin only)

## 6. Complete endpoint reference

Base URL: `http://localhost:8080`

| Method | Endpoint | Access | Purpose | Expected success |
|---|---|---|---|---|
| POST | `/api/auth/register` | Public | Register a customer | 201 |
| POST | `/api/auth/login` | Public | Login and receive JWT | 200 |
| GET | `/api/books` | Public | List books; optional `?search=term` | 200 |
| GET | `/api/books/page` | Public | Paginated/sorted book list | 200 |
| GET | `/api/books/{id}` | Public | Get book by ID | 200 |
| POST | `/api/books` | ADMIN | Create book | 201 |
| PUT | `/api/books/{id}` | ADMIN | Update book | 200 |
| DELETE | `/api/books/{id}` | ADMIN | Delete book | 204 |
| GET | `/api/cart` | Authenticated | Get current user's cart | 200 |
| POST | `/api/cart/items` | Authenticated | Add a book to cart | 201 |
| PATCH | `/api/cart/items/{bookId}` | Authenticated | Set cart quantity | 200 |
| DELETE | `/api/cart/items/{bookId}` | Authenticated | Remove a cart item | 204 |
| POST | `/api/orders/checkout` | Authenticated | Create an order from cart | 201 |
| GET | `/api/orders` | Authenticated | List current user's orders | 200 |
| GET | `/api/orders/{id}` | Owner or ADMIN | Retrieve order details | 200 |

### Pagination examples

```http
GET {{baseUrl}}/api/books/page?page=0&size=2
GET {{baseUrl}}/api/books/page?page=1&size=2
GET {{baseUrl}}/api/books/page?search=java&page=0&size=5
GET {{baseUrl}}/api/books/page?page=0&size=10&sortBy=price&direction=desc
```

Supported parameters: `page` (zero-based, default `0`), `size` (default `10`, allowed `1`–`100`), `search` (optional), `sortBy` (`title`, `author`, `price`, `stock`, `id`), and `direction` (`asc` or `desc`). Invalid page/size/sort parameters should return `400 Bad Request`.

## 7. Negative tests to include in reviewer evidence

| Scenario | Request | Expected result |
|---|---|---|
| Invalid email on registration | `POST /api/auth/register` | 400 |
| Password shorter than 8 chars | `POST /api/auth/register` | 400 |
| Register same email twice | `POST /api/auth/register` | 409 |
| Wrong password | `POST /api/auth/login` | 401 |
| Call cart without token | `GET /api/cart` | 401 |
| Use invalid/expired token | Any protected endpoint | 401 |
| Customer tries to create book | `POST /api/books` with customer token | 403 |
| Unknown book ID | `GET /api/books/99999` | 404 |
| Add quantity greater than stock | `POST /api/cart/items` | 409 |
| Checkout empty cart | `POST /api/orders/checkout` | 400 |
| Invalid page/size | `GET /api/books/page?size=101` | 400 |

For each test, record the actual status code and result. Do not mark a test as passed until you have run it.

## 9. Logs and request tracing

Each API request is logged with HTTP method, path, response status, duration, and a request ID. The response includes an `X-Request-Id` header. Use the ID to correlate the request with backend log entries. Never share passwords, JWTs, or authorization headers in screenshots or logs.

## 10. Troubleshooting

- **`mvn` not recognized:** install/configure Maven, reopen the terminal, then run `mvn -version`.
- **Port 8080 is occupied:** run `$env:PORT = "8081"` before `mvn spring-boot:run`; use `http://localhost:8081` in Postman.
- **401 on protected endpoint:** log in again and use only the token string in Bearer Token configuration.
- **403 creating/updating/deleting books:** use the administrator token, not a customer token.
- **Data disappeared:** expected with H2 in-memory mode after application shutdown.
- **Admin login fails:** check that `app.seed-admin.enabled` is not set to `false` and that startup completed without seed errors.

## 11. Architecture and Design Decisions

### Application Architecture

The backend follows a layered architecture using Spring Boot.

- **API layer (`api`):** Exposes REST endpoints and handles HTTP requests and responses.
- **Service layer (`service`):** Implements business logic for authentication, book management, cart operations, and order processing.
- **Repository layer (`repo`):** Uses Spring Data JPA repositories to access persisted data.
- **Domain layer (`domain`):** Contains the application's domain entities.
- **Security layer (`security`):** Handles JWT-based authentication and request authorization.
- **Configuration layer (`config`):** Contains application configuration and development setup.
- **Error layer (`error`):** Centralizes exception handling and API error responses.

### Key Design Decisions

1. **Dependency injection:** Spring manages application components and their dependencies, supporting separation of concerns and testability.
2. **DTOs for API contracts:** Request and response DTOs separate API representations from persistence entities.
3. **Repository pattern:** Data access is separated from business logic through Spring Data JPA repositories.
4. **Transactional checkout:** Checkout operations should maintain data consistency across order creation, inventory updates, and cart changes.
5. **Centralized exception handling:** A global exception handler helps return consistent error responses and appropriate HTTP status codes.
6. **JWT-based security:** Token-based authentication protects endpoints that require an authenticated user, with authorization rules applied where configured.
7. **Validation:** Request validation helps reject invalid input before it reaches business logic.

### Testing Strategy

The automated test suite should cover the relevant application layers:

- **API and validation tests:** Verify request validation and HTTP behavior.
- **Controller tests:** Verify endpoint behavior and responses.
- **Service tests:** Verify business rules and service behavior.
- **Domain tests:** Verify domain object behavior and invariants.
- **Exception-handling tests:** Verify error responses and HTTP status codes.

Run the test suite before committing changes:

```powershell
.\mvnw.cmd clean test
```

Only report the tests as passing after the command completes successfully.

### Local Development and Security Notes

- The default local setup uses an in-memory H2 database; its data is reset when the application stops.
- Development credentials and fallback JWT secrets are for local testing only and must not be reused in deployed environments.
- Configure a persistent database, production-grade secrets, and additional security controls before deploying to a production environment.
